- *Cost:* Hardware and network costs are typically sunk or covered by the institution, meaning zero monthly out-of-pocket expenses for the research grant.
- *Zero-Latency Environment:* If the experiment is conducted entirely in a campus computer lab, the local network will provide near-instantaneous WebSocket connections for the collaborative text editor.

*Disadvantages:*
- *IT Bureaucracy and WebSockets:* Real-time applications require opening specific, non-standard network ports (e.g., port 6001 for Laravel Reverb) and configuring reverse proxies. University IT security policies are notoriously strict, and getting approval for these custom server configurations can delay a project by weeks or months.
- *Accessibility:* If you want students to participate in the experiment from home or a dorm room, configuring external access (like a VPN or public IP) through a university firewall can be highly restrictive.
- *Maintenance:* If the server crashes or the database corrupts, your team is completely dependent on campus IT hours and response times to restore it.

### 2. Cloud Service (DigitalOcean, AWS, Linode)
Renting virtual private servers (VPS) hosted in a commercial data center.

*Advantages:*
- *Total Autonomy and Speed:* Your research team gets full "root" access immediately. You can install PHP, PostgreSQL, Redis, and configure WebSocket ports in an afternoon without waiting for IT department approvals.
- *Managed Databases:* Platforms like DigitalOcean offer "Managed PostgreSQL." For a few extra dollars, the cloud provider automatically handles daily backups, software updates, and failure recovery. This virtually eliminates the risk of losing your experimental data to a server crash.
- *Universal Access:* The application is live on the open web. Students can participate seamlessly from any location or device, which is essential if the study involves homework or remote collaboration.

*Disadvantages:*
- *Recurring Costs:* Cloud hosting requires a monthly budget. However, for an experiment with ~120 students, a robust setup on DigitalOcean typically costs between $20 to $40 per month.
- *Data Anonymization Requirements:* Because the data is stored on third-party servers, you must ensure strict anonymization. You cannot store real student names or school IDs; you must use randomized aliases to comply with standard academic data protection policies.

### The Most Suitable Option: Cloud Hosting (e.g., DigitalOcean)
For a modern, real-time application using Laravel, WebSockets, and external AI APIs, *a cloud service is the most suitable option.*

The primary reason is developmental agility. Building a synchronous collaborative editor requires rapid iteration, frequent server restarts, and custom port routing. The friction of university IT firewalls is often the number one bottleneck for software-based research.

By using a cloud provider, your team retains absolute control over the environment. You can deploy the app quickly, allow students to access it from anywhere, and rely on automated, enterprise-grade database backups to protect your research data. To satisfy ethics and privacy requirements, simply design the database to use anonymized user tokens rather than personally identifiable information.

Here is the high-level deployment roadmap for getting Study 2 live on a cloud provider like DigitalOcean or AWS.

### 1. The Infrastructure Layout
To balance performance with ease of management, you should separate your application server from your data layer.
- *The App Server (Droplet/EC2):* A standard Linux server (Ubuntu) running Nginx, PHP 8.x, and Node.js. Nginx will serve your React frontend and act as a reverse proxy for your Laravel backend and WebSocket traffic.
- *The Data Layer (Managed Services):*
  - *Managed PostgreSQL:* Offload your database to a managed cluster. This ensures your experimental telemetry data is automatically backed up daily and removes the headache of manual database tuning.
  - *Redis:* You can install Redis directly on the App Server to handle the WebSocket broadcasting and temporary state storage (like the blind polling votes) without needing a separate managed instance.

### 2. Server Provisioning & Management
While you could SSH into a raw Ubuntu server and manually install PHP, Composer, and Nginx, the most efficient route for this specific stack is using a server management tool designed for Laravel.

*Laravel Forge* is the industry standard here. You link it to your cloud provider account, and it automatically provisions the server, installs the required software, configures Nginx, and secures the server with a firewall. It essentially acts as your automated DevOps engineer, allowing you to focus on the research code rather than server administration.

### 3. Configuring the Real-Time Layer (The Tricky Part)
Deploying a standard web app is straightforward; deploying WebSockets requires specific configurations to ensure the connections stay alive and secure.
- *Daemonizing Reverb:* Laravel Reverb (your WebSocket server) needs to run continuously in the background. You will need to configure *Supervisor* (a process monitor for Linux) to keep the `php artisan reverb:start` process running and automatically restart it if it crashes.
- *Daemonizing Queue Workers:* To prevent the websocket broadcasts from slowing down the HTTP requests, your events should be queued. Supervisor will also need to manage your `php artisan queue:work` processes.
- *SSL and WSS:* Browsers will block WebSocket connections on a secure site (HTTPS) unless the WebSocket connection is also secure (WSS). You will need to provision an SSL certificate (e.g., via Let's Encrypt) and configure Nginx to proxy traffic from a specific port (like 6001) or a specific path securely to the Reverb server.

### 4. Continuous Deployment (CI/CD)
Because this is an active research project, you will likely be pushing updates and tweaking the AI prompts frequently.
- Connect your server to your Git repository (GitHub/GitLab).
- Configure a deployment script that automatically pulls the latest code, installs dependencies (`composer install` and `npm install`), compiles the React frontend (`npm run build`), and gracefully restarts the PHP-FPM and Reverb services whenever you push to the main branch.

Once the server is built, you attach your application to it.

```bash

Step 4: Configuring the Real-Time Engine (The Critical Step)
This is where Forge really pays off. WebSockets require long-running background processes. In Forge, you manage these using the Daemons tab (which configures Supervisor under the hood).
You need to create two Daemons:
1. The Queue Worker:
Command: php artisan queue:work --timeout=0
Why: This ensures that when 60 students type at the same time, the database logging happens in the background without slowing down the app.
2. The Reverb Server (WebSockets):
Command: php artisan reverb:start
Why: This keeps the WebSocket server alive to instantly transmit text edits between students in the collaborative workspace.
Note: Forge will monitor these daemons. If they crash, Forge automatically restarts them in seconds.
Step 5: Securing the WebSockets (SSL)
Browsers will block the collaborative text editor if the WebSockets aren't secure (wss:// instead of ws://).
1. Obtain an SSL Certificate: In the Forge "SSL" tab for your site, click "Let's Encrypt" and generate a free certificate.
2. Reverb Configuration: Laravel Reverb is designed to integrate seamlessly with Forge. Once your SSL is active, Reverb will automatically securely route the WebSocket traffic through Nginx on the standard HTTPS port (443), meaning you rarely have to mess with custom port forwarding.
